# RL78_F24_UART_Xmodem_Demo

Standalone RL78/F24 UART Xmodem communication demonstration. Tera Term or another
Xmodem terminal sends data directly to UART1; UART0 provides commands and text logs.

| Interface | Pins | Purpose |
| --- | --- | --- |
| UART0 | P15 TX / P16 RX | Diagnostic terminal and keyboard commands |
| UART1 | P74 TX / P75 RX | Xmodem data from the PC |

Use the serial settings generated by this project's Smart Configurator inputs.
Connect crossed UART TX/RX with a common ground and compatible signal levels.

## Operation

1. Open the UART0 diagnostic terminal and enter `1` to start reception.
2. Use Tera Term on the UART1 connection to send a file, such as the included
   `test_for_xmodem.bin`, with Xmodem.
3. Observe packet/address/byte-count messages on UART0. Successful reception
   requests an MCU reset through the existing illegal-access mechanism.

The receiver accepts 128-byte and 1-KiB blocks. `XMD_Write()` currently returns
success without programming Flash. The `FLASH_AREA` argument and `(boot)` text
labels are retained from the original demonstration; there is no Boot/App image
validation or firmware-update contract in this example.

This project's workflow is independent of the ISP Tool's
`RL78_F24_Xmodem_Transfer` diagnostic target and its framed control protocol.

## CS+ and build

- Open `RL78_F24_UART_Xmodem_Demo.mtpj` in CS+ for CC.
- Edit peripherals through `RL78_F24_UART_Xmodem_Demo.scfg` and retain the existing
  generated-source bindings, startup, clocks, vectors and linker options.
- Rebuild in CS+, or run `powershell -NoProfile -ExecutionPolicy Bypass -File .\build.ps1`.
- `DefaultBuild/RL78_F24_UART_Xmodem_Demo.mot` is the standalone programmer output;
  it is not an ISP App update BIN. Compilation does not program a connected board.
- `scripts/clean_obj.bat` removes only allowlisted compiler intermediates. Images,
  maps, libraries, local settings and logs are retained.

- Normal builds compile the current editable sources.
- The publisher checks runtime/configuration identities in `scripts/runtime_contract.json`.
- Functional firmware publication requires a separately reviewed contract and matching hardware acceptance.
